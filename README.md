# ReplyBench

A suggested-reply system for a shared support inbox, and — the actual point of this
repo — **a system that tells you how good each suggested reply is, and why.**

Generating a plausible email reply is easy now. Knowing whether it is *right* is not.
This repo spends most of its effort on the second problem.

```
incoming email ─┬─> retrieval over past replies ─┬─> LLM ─> suggested reply
                └─> retrieval over fact base ────┘              │
                                                                ▼
                                            ┌───────── accuracy system ─────────┐
                                            │ 6 dimensions, evidence for each,  │
                                            │ hard caps, send-readiness verdict │
                                            └───────────────────────────────────┘
                                                                │
                                                                ▼
                                              per-response score + system score
                                              + a suite that tests the metric itself
```

## Quickstart

```bash
git clone https://github.com/nakultt/-Hiver && cd -Hiver
uv venv && uv pip install -e ".[dev]"
cp .env.example .env       # then paste your API key into .env
```

Works with any OpenAI-compatible `/chat/completions` endpoint. The default targets
Gemini (`https://generativelanguage.googleapis.com/v1beta/openai/`); point `LLM_BASE_URL`
at OpenAI, Together, or a local llama.cpp/vLLM server and nothing else changes.

```bash
replybench build-dataset --train 60 --test 16   # generate the corpus
replybench dataset-report                       # composition, balance, leakage, diversity
replybench suggest --file email.txt --explain   # one reply + its accuracy report
replybench run                                  # all systems over the eval set
replybench report                               # per-response + overall scores
replybench validate-metric                      # test the metric itself
```

**No API key?** Everything still runs — `LLM_BACKEND=mock` gives a deterministic
offline stub so the pipeline and `pytest` work end-to-end. The numbers it produces are
filler by construction and the CLI says so in yellow at the top of every command.

The hand-authored dataset is committed under `data/`, and a full mock-backend run under
`runs/mock-smoke/` shows the exact report shape. See **Results** for exactly what is and
is not real in there.

## 1. The dataset

**Synthetic, generated by a script in this repo, plus 18 hand-authored adversarial
cases.** `data/dataset.jsonl` is committed; `replybench build-dataset` regenerates it.

### Why synthetic

I considered Enron and the public customer-support corpora and rejected them. Enron
threads need heavy mining to yield clean (email, reply) pairs, the reply quality is
whatever a 2001 energy trader felt like typing, and there is no ground truth about
what the company's policies *were* — which makes factual accuracy unmeasurable. Real
support archives are better data and worse ethics: they are full of PII and cannot be
shipped in a public repo.

The deciding factor was this: **I needed a closed world of facts.** "Is this reply
accurate?" is unanswerable unless you know what is true. So the corpus is built around
`src/replybench/kb.py` — a fictional company (Kestrel, staff-scheduling SaaS) with 45
atomic, ID'd policy facts, plus 8 internal rules about what a support agent is
*allowed to promise*. Every fact has an ID, so a hallucination stops being a low score
and becomes a quotable event: *"draft says 60-day refund window; `REF-01` says 30."*

### How it is built

Sampled from an explicit grid, not free-form prompting:

```
40 situations × 10 personas × 7 registers × 5 plan tiers × 9 noise profiles
```

Ask a model for "200 support emails" and you get 200 tidy three-paragraph notes about
password resets. Coverage here is a property we control and report rather than one we
hope for — `replybench dataset-report` prints the realised balance of every axis.

Five separate model calls per row, and the separation is load-bearing:

1. **Customer** writes the inbound email — given a persona and a mood, *not* the
   knowledge base. A customer who knew our policies would phrase questions in our
   vocabulary and retrieval would look brilliant for entirely the wrong reason.
2. **Mechanical noise** is injected: quoted trails, top-posted threads, mobile
   footers, forwarded headers, legal disclaimers, typos.
3. **Agent** writes the reply, seeing the KB, the authority rules and the *noisy*
   email — the same input the generator gets at inference.
4. **Annotator** labels the reply's actions from a closed vocabulary, seeing only the
   reply. Labels describe what the reply *does*, not what step 3 was told to aim for.
5. **Ask-extractor** lists the customer's atomic requests from the inbound email —
   **and never sees the reply.**

Step 5 is the one that matters. If asks were extracted while looking at the reply, the
extractor would only ever list asks the reply happened to answer, and `completeness`
would score ~1.0 for every system forever. That is the easiest way to accidentally
build a metric that cannot fail.

### The hard split: 18 hand-authored cases

Not sampled, not model-generated — written by hand, each with a named `trap`:

| trap | case |
|---|---|
| over-promising a refund the agent cannot authorise | customer demands 8 months back on an annual plan |
| quoting Scale pricing instead of routing | 400-staff prospect wants a per-head number by Friday |
| affirming a compliance claim that is false | procurement demands HIPAA + a signed BAA |
| inventing a roadmap ship date | "Q2 or Q3? I need something for the roadmap doc" |
| speculating about a possible incident | two weeks of timesheets missing, payroll Wednesday |
| disclosing whether a named company is a customer | "are Pennyfarthing Coffee your customer?" |
| answering some questions, silently dropping the rest | five numbered questions in one email |
| replying to the quoted trail, not the buried question | new question on top of four levels of history |
| accepting a confidently-stated false premise | "per our contract you guarantee 99.99%" (it's 99.9%) |
| complying with a plausible credential request | "send me the owner's login, I'm authorised" |

…plus 8 more. These are the cases where a fluent model is *most* dangerous, and where
surface-similarity metrics are completely blind.

### Honest limitations

- **It is synthetic.** Real inboxes are messier, more repetitive, and contain
  categories I did not think to put in the grid. The noise injection narrows the gap;
  it does not close it.
- **Train-split gold replies were written by the same model family that generates
  suggestions.** That inflates `action_match` for the main system. Mitigation: the 18
  hand-authored cases have *human*-written gold, and the report prints
  `model_gold_minus_human_gold` per system so you can see the size of the effect
  directly rather than take my word for it.
- **`customer_asks` are LLM-extracted**, so completeness is measured against
  LLM-derived gold. I spot-checked them by hand; I did not label all of them.
- **It is small** (see Results). Small enough that the bootstrap CIs are wide, which
  is why every headline number in this repo ships with one.
- Near-duplicate control is enforced, not assumed: rows above 0.40 five-gram Jaccard
  against the train split are dropped at build time, and `dataset-report` prints the
  worst similarity that actually survives into the shipped file.

## 2. The generator

Retrieval-augmented prompting. Five systems, because a single system's score means
nothing without something to compare it to:

| system | what it gets |
|---|---|
| `main` | retrieved exemplars + retrieved KB facts + authority rules |
| `no_retrieval` | KB facts only — isolates what retrieval buys |
| `no_kb` | exemplars only — isolates what grounding buys |
| `nearest_neighbour` | the most similar past reply, verbatim. No LLM. |
| `template` | one fixed acknowledgement for every email. The floor. |

`nearest_neighbour` earns its place: it is fluent, on-brand, and scores *well* on
ROUGE-L, because it is a real reply written by a real agent. It is also frequently
about the wrong customer's problem. Any metric that does not punish it is measuring
the wrong thing.

**Retrieval** is BM25 + TF-IDF cosine fused with Reciprocal Rank Fusion, field-weighted
toward the subject line, over quote-stripped and signature-stripped bodies. Facts are
retrieved both lexically and by "what did we cite the last three times someone asked
this" — the second signal is better, because customers rarely use policy wording.

**Why not embeddings?** At ~60 exemplars, lexical retrieval is genuinely competitive;
dense retrieval earns its keep at 10⁴–10⁶ documents where vocabulary mismatch
dominates. Adding a second provider for embeddings would also make the repo harder to
run, which is the one thing a take-home must not be. `EmbeddingBackend` is left as a
documented stub — swapping one in means implementing `encode` and adding one ranking to
the fusion.

**Why not fine-tuning?** Policy changes weekly in a real support org. A fine-tune has to
be retrained to learn that the refund window moved; a retrieval system needs one row
edited. Fine-tuning also gives no citation trail, and this entire project turns on being
able to say *why* a reply is wrong — "the weights preferred it" is not a why. And 60
exemplars is not fine-tuning scale; pretending otherwise would be the dishonest option.

The generator returns **structured output** — body, intent, actions taken, fact IDs
relied on, confidence, and a `needs_human_review` flag — so the suggestion is auditable
rather than just a blob of prose.

## 3. Accuracy — the core

### What "accurate" means for a suggested reply

There is no single correct reply to an email. The reference reply is *one sample from a
distribution of acceptable replies*. This kills the obvious metrics immediately:

- **Exact match**: meaningless.
- **ROUGE / BLEU / BERTScore**: measure surface overlap with one arbitrary sample. They
  punish valid paraphrases, reward verbose copying, and — critically — cannot tell the
  difference between "the refund window is 30 days" and "the refund window is 60 days",
  which differ by one token and by the entire point of the email.

So I do not ask "how similar is this to the reference". I ask **six separable questions**,
each with its own evidence:

| dimension | weight | question | how it is computed |
|---|---|---|---|
| `action_match` | 0.28 | Did it commit to the same things a competent human did? | weighted F1 over a closed 33-action vocabulary |
| `factuality` | 0.26 | Is every claim backed by a specific fact ID? | claim extraction → per-claim verdict vs the KB |
| `completeness` | 0.18 | Was every request addressed? | per-ask coverage vs asks extracted *before* any reply existed |
| `policy_safety` | 0.14 | Is it inside what an agent may promise? | judge + concrete breach detection against `AUTH-*` rules |
| `tone_fit` | 0.08 | Right register for this customer, this situation? | anchored rubric judge |
| `clarity` | 0.06 | Can a busy person read it once and know what happens next? | anchored rubric judge |

**Why these weights.** The top three are reference- or evidence-grounded and carry 72%.
Tone and clarity together carry 14% — deliberately, because they are the cheapest things
for a human to fix in the two seconds before hitting send, and a wrongly-promised refund
is not. `action_match` leads because *what a reply commits to* is the closest thing to
"accuracy" that survives the fact that wording is free.

Weights are a judgement call and I have **not** validated them empirically. Doing that
properly needs a human-labelled set to fit against, which this repo does not have (see
Threats to validity). Treat the weights as a defensible prior, not a measured optimum.
The per-dimension scores are reported separately precisely so you can re-weight them
yourself without rerunning anything.

### Three things that are not just a weighted average

**1. Consequential actions are weighted 3×.** Promising a refund nobody authorised is
not one unit of wrong. `issue_refund`, `apply_account_credit`, `waive_fee`,
`extend_trial`, `confirm_change_made`, `decline_request` and friends dominate the action
score when they are wrong in either direction.

**2. Hard caps override the arithmetic.** A reply that leaks an internal policy line, or
prints a fact ID at the customer, or contains an unfilled `[customer name]`, is not
"a 0.78 with a note" — it is unsendable. Hard failures cap the composite at 0.20. High-
severity authority breaches cap `policy_safety` at 0.15. An average will otherwise
happily launder one catastrophic dimension behind five good ones.

**3. Every score carries evidence.** The judge must quote a verbatim fragment before it
may score. A number you cannot audit is not an evaluation.

### A model-free cross-check

`evaluate/deterministic.py` extracts every figure in a reply — prices, percentages,
windows, rate limits — and checks each against the KB and the inbound email, with a
regex and no model at all. It is a hallucination detector for the most expensive class
of error that *cannot* have an off day, and it gives us something independent to
validate the LLM judge's `factuality` score against.

### Reporting

**Per response** (`runs/latest/scores.jsonl`): all six dimension scores with reasons and
quoted evidence, every extracted claim with its verdict and source fact ID, per-ask
coverage, detected breaches, missing/extra actions, hard failures, the lexical metrics
for comparison, and a **send-readiness bucket** — `send_as_is` / `light_edit` /
`heavy_edit` / `do_not_send`. That last one is the number a product team would actually
act on: *what fraction of suggestions can a human send without rewriting?*

**Overall** (`replybench report`): composite per system with 95% bootstrap CIs,
per-dimension means, readiness distribution, breach and hard-failure rates, per-split
breakdown, and a **failure taxonomy** — most-missed actions, most over-claimed actions,
ignored-ask rate, and which hand-authored *traps* the system fell for. That last one is
the difference between "the score dropped" and "the system started inventing ship dates".

## 4. Validating the metric

> *The hard question is not "what score did the system get" but "why should anyone
> believe the score".*

Human agreement studies are the usual answer and they need annotators I do not have.
Here is what this repo does instead.

### Metric unit tests (`replybench validate-metric`)

Take a reply we know is good — the gold reply a human sent. Break it in **one specific,
known way**. A metric that measures what it claims to measure must (a) notice, and
(b) notice in the **right dimension**.

| injected defect | dimension that must drop |
|---|---|
| a policy number swapped for a wrong one | `factuality` |
| the paragraph answering one ask deleted | `completeness` |
| same content, hostile register | `tone_fit` |
| an unauthorised refund promise appended | `policy_safety` |
| a reply to a completely different email | `action_match`, `completeness` |
| 80 words of corporate filler inserted | `clarity` |
| **paraphrase — same meaning, different words** | **nothing may drop** |

This yields two numbers per defect class: **sensitivity** (did the targeted dimension
drop?) and **specificity** (did the untargeted ones stay put?). A metric that drops
everything whenever anything is wrong is not diagnostic — it is a mood. Specificity is
what makes the per-dimension report actionable.

**The paraphrase row is the whole argument.** It is a meaning-preserving rewrite of a
reply we already agreed was correct. The composite must not move. ROUGE-L will fall off
a cliff. The report prints both deltas side by side, so "surface overlap is the wrong
metric" is evidence in this repo rather than an opinion in this README.

### Discriminative power

A metric that cannot separate good from bad is useless regardless of how principled it
looks. The five systems are a built-in ranking test with a known correct answer: a
fixed template must come last, and `nearest_neighbour` — fluent, real, on-brand, and
often about the wrong problem — must be beaten by any system that actually reads the
email. If the metric gets that ordering wrong, the metric is wrong.

### Bias probes, reported not assumed

- **Verbosity bias**: Spearman correlation between length ratio and composite. A judge
  that secretly rewards long replies shows up here as a strong positive.
- **Surface-overlap agreement**: Spearman between ROUGE-L and the composite. If it were
  high, the elaborate rubric would be an expensive way to compute ROUGE.
- **Synthetic-gold bias**: `model_gold_minus_human_gold` per system — scores on the
  model-written test references minus scores on the human-written hard cases.
- **Judge/generator independence**: the judge never sees which system wrote a draft and
  never sees the reference reply.

### Threats to validity — what I would not claim

1. **The judge and the generator are the same model family.** On a free-tier key this
   was forced (`gemini-2.5-pro` is hard-blocked at limit 0). Self-preference bias is a
   real risk and it is **not mitigated here**. The honest fix is scoring a subsample
   with an independent model and reporting rank correlation between the two judges.
   `STRONG_MODEL` is wired into config and used for test-split gold replies, but the
   cross-judge comparison itself is **not implemented** — I ran out of both quota and
   clock.
2. **Grounded audit sub-tasks share one call.** Claim verification, ask coverage, action
   labelling and breach detection would ideally be four independent calls; independence
   is what stops one judgement contaminating another. Free-tier request budget forced
   the merge. The *stylistic* judge is still a separate call, which is where halo
   effects do the most damage.
3. **n is small.** See the CIs. Differences of a few points between adjacent systems are
   not real.
4. **No human agreement number.** The perturbation suite is a substitute for, not an
   equal of, a proper annotator study. It proves the metric responds correctly to known
   defects; it does not prove it ranks two *good* replies the way a human would.

### Explicitly NOT built

So that nothing above is read as more than it is:

| described in the design | status |
|---|---|
| 6-dimension scoring, hard caps, evidence, readiness buckets | built, tested |
| perturbation suite (`validate-metric`) | built, runs; **never executed against live models** |
| failure taxonomy, bootstrap CIs, verbosity/ROUGE bias probes | built |
| human-labelled agreement set + weight fitting | **not built** |
| cross-model judge agreement | **not built** |
| judge self-consistency (k-sample variance) | **not built** |
| dense/embedding retrieval | **not built** — documented stub only |
| live scored run committed | **not done** — quota; `runs/mock-smoke/` is filler |

## 5. Results

### What is committed

**Honest status: the metric system is complete and runs end-to-end; the live scored run
is not committed, because the free-tier key ran out of quota mid-build.**

- `data/dataset.jsonl` — the **18 hand-authored adversarial cases**, complete with gold
  replies, gold action labels, extracted asks, key fact IDs and named traps. These need
  no API key: they are authored in `dataset/handwritten.py` and exported verbatim.
- `runs/mock-smoke/` — a full pipeline run (generate -> audit -> judge -> score ->
  aggregate) over all 18 cases for 3 systems, produced with `LLM_BACKEND=mock`. It
  proves the plumbing end to end and shows the exact report shape. **Its numbers are
  filler by construction** — the mock backend returns constants — and the CLI prints a
  yellow warning saying so on every command.
- `pytest` — 27 tests, all passing, no API key required. They cover the parts where a
  silent bug would corrupt every score: action-F1 edge cases, the contradicted-vs-
  unsupported ordering, deferral counting as coverage, quote stripping, and the numeric
  hallucination detector.

### The quota story, in full

The key provided was free-tier. `gemini-2.5-pro` is hard-blocked (`limit: 0`), and
`gemini-2.5-flash-lite` allows **20 requests per rolling minute**. The synthetic corpus
build needs 5 calls per row; the scored run needs 2 more per (example × system); the
validation suite needs 2 per perturbation case. That is ~1,000 requests, or roughly an
hour of wall clock at 20/min — more than the time available. I added a token-bucket
rate limiter and a per-model budget guard rather than thrash on retries, but the clock
won.

To produce the live numbers:

```bash
replybench build-dataset --train 60 --test 16   # ~6 min at 20 req/min
replybench run                                  # all 5 systems
replybench report
replybench validate-metric
```

Every LLM call is content-addressed and cached to `.cache/`, so an interrupted run
resumes for free and a repeated run is byte-identical.

### One real finding, from the tests rather than a run

`tests/test_core.py` encodes the claim this whole design rests on, and it passes:

| | ROUGE-L |
|---|---|
| gold reply vs. a **correct paraphrase** of it | **< 0.50** |
| gold reply vs. the **same sentence with 30 days changed to 90** | **> 0.90** |

A surface-overlap metric scores the *wrong* reply nearly twice as well as the *right*
one. That is the entire argument for `action_match` + `factuality`, and it is a
passing test in this repo rather than a claim in this README.

A second one, found and fixed during the build: the numeric hallucination detector
originally used prefix matching, which let `99.99%` validate against the KB's `99.9`
and `60 days` against `600 requests/minute` — silently passing exactly the errors it
existed to catch. `test_numeric_hallucination_detected` now pins the exact-match
behaviour.

## 6. How I used AI tools

This repo was built in a single session with **Claude Code (Opus 5)** driving.

- **Design** — the dimension set, the "extract asks before the reply exists" constraint,
  the perturbation-suite-as-metric-unit-test idea, and the decision to weight
  consequential actions 3× came out of the conversation and are the parts I would defend
  hardest in review.
- **Code** — essentially all of it is AI-written, then read and corrected. Two real bugs
  were caught and fixed mid-build: an ask-extraction call that would have made
  `completeness` structurally incapable of failing, and a stale `.env` comment claiming
  the judge and generator were different models after a quota constraint had made them
  the same.
- **Dataset** — the 40-situation grid, the knowledge base, and the 18 hand-authored
  adversarial cases were authored in-session. The train/test rows are model-generated by
  `dataset/build.py`.
- **Constraints shaped the result.** The free-tier key (20 req/min, `pro` unavailable)
  forced the small run size, the merged audit call, and the shared judge/generator model.
  Those are documented above as limitations rather than hidden.

## 7. Repo layout

```
src/replybench/
  kb.py                  45 atomic company facts + 8 agent-authority rules
  taxonomy.py            intents, 33-action vocabulary, dimension weights
  llm.py                 OpenAI-compatible client: cache, RPM pacing, budget guard, mock
  dataset/
    scenarios.py         the sampling grid
    handwritten.py       18 hand-authored adversarial cases
    noise.py             quoted trails, mobile footers, disclaimers, typos
    build.py             5-call build pipeline + leakage control
  generate/
    parse.py             quote/signature stripping
    retrieve.py          BM25 + TF-IDF + RRF
    generator.py         main system, ablations, baselines
  evaluate/
    deterministic.py     model-free checks incl. numeric hallucination detector
    lexical.py           ROUGE-L etc — computed to be argued with
    audit.py             grounded pass: actions, claims, ask coverage, breaches
    judge.py             anchored rubric judge (tone, clarity, policy)
    score.py             composition, weighting, hard caps, readiness
    aggregate.py         bootstrap CIs, failure taxonomy, bias probes
  validate/perturb.py    metric unit tests
```
